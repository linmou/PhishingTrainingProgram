## All six attacks

Every new probe uses actual staging HTTP with public anon or real signed authenticated-role credentials, an existing assessment question, and a privileged persisted-state oracle. The service credential is used only for fixtures/inspection/cleanup. The authenticated-role account is created through the real Auth admin API and signed in with the public client; passwords/tokens remain in memory and are never stored in evidence. If that fixture cannot be provisioned, its cases remain blocked. No injected rejection or UI hiding can pass these probes. Errors with unrelated codes, server errors and disabled-feature responses fail rather than count as denials. The output never saves the private review body returned by a successful impersonation. All six cases start explicitly blocked; state-oracle failures are saved before aborting further attacks, and the outsider fixture deletion is read back and recorded. A failed outsider cleanup propagates to the main runner and retains the staging project lease even if room cleanup succeeds.

## Deployment readiness and non-destructive rollback

Use [Supabase release verification](supabase-release-workflow.md#verification-scope) and [project coordination](agent-coordination.md). Behavior tests do not authorize activation or produce a release verdict. For a separately authorized staging rollback drill, the release owner must:

1. Record environment, candidate/source hashes, shared lease, dependencies and actual hosted flag observation. The code default is true; an absent variable and an observed explicit value are different facts. If observation is unavailable, record **unknown** rather than the old config's expected disabled state.
2. Record normal preparation/delivery outcome and counts/identities for existing questions, attempts, events and saved results before any configuration change. Preserve the current configuration for restoration.
3. Disable new work through the configured release procedure, verify rejected assessment operations, existing history readability and unchanged authority/history. The current handler blocks assessment operations while disabled except owner `clear_chat_history`; a rollback drill must **not call clear** or delete any evidence. Do not assume grading or historical readiness continues while disabled; verify the selected application's resulting behavior.
4. Restore the exact prior configuration if the approved drill requires it, verify affected behavior, record actual outcomes and retain failed checks. No secret values in reports; no fixture reset standing in for a rollback test. Production requires its own release decision and verification, and is outside this issue's automatic tests.

No flag observation, activation, deployment, destructive reset or rollback drill occurred during this audit. The version-scoped exception remains unchanged, and does not waive future verification.

## Learner privacy acceptance implementation

`assessment-privacy.js` uses two existing staging fixture rooms for a pass and a retry→terminal-failure journey. It seeds unique private values in transfer basis, reviewed rationale/raw output and the actual private provider-attempt store. The provider row is explicitly `privacy_fixture_only` with `SYNTHETIC_PRIVACY_FIXTURE`; it is not a real provider call, a valid provider attempt, a model-quality result or release evidence. Fixture cleanup is the normal coordinated runner cleanup.

The collector scans HTTP request/response bodies (not credentials/headers or application bundles), real `postgres_changes` message records, learner DOM, actual downloaded JSON/TXT bytes and a real denied private-review response. It scans structured private fields and renamed/encoded private values, including private material used as object keys. Heartbeats do not count as row-change evidence; unreadable captures fail rather than silently pass. Evidence retains hashes, counts/paths and violations, not raw learner/private response bodies. Temporary download files are removed after scanning, including failures.

Only the exact saved second-failure result can authorize publication. The workflow first verifies the private assessment is failed after two attempts and that the private second answer matches the saved event, then permits that exact result in room history/exports and the tightly bound legacy terminal-feedback envelope. Retry and pass never disclose the stored key/explanation; transfer basis/rationale/provider values stay forbidden throughout. The offline inspector/collector tests and a real local HTTP/WebSocket browser harness verify instrumentation, not hosted application privacy.

The direct-role SQL test is now a standalone transaction. Run it and the current lifecycle/result tests only on a verified disposable migrated baseline with `psql -X -v ON_ERROR_STOP=1 -f ...`. All fixtures roll back. This PR supplies no exported database and makes no claim that static inspection or local browser fixtures validate the deployed schema.
