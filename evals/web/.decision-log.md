# Decision Log: Prompt Evaluation Review Workspace PRD

Intent: preserve product decisions and overrides made while refactoring the PRD so later UX, architecture, and implementation work can revise them deliberately.

## 2026-06-21

- Decision: Treat the existing `evals/web/PRD.md` as an update/refactor target rather than creating a separate PRD workspace.
  - Rationale: The existing PRD already describes this standalone website and is the closest artifact to the requested work.

- Decision: Use Fast path for PRD authoring.
  - Rationale: The user explicitly asked Codex to decide micro-decisions and produce an outcome for review.

- Decision: Position the product as a non-technical Prompt Evaluation Review Workspace.
  - Rationale: The core user need is not editing files; it is making trustworthy review decisions from prompt evaluation evidence.

- Decision: Earlier direction used a dedicated promotion-review page as the top-level workflow.
  - Rationale: Non-technical reviewers appeared to need a verdict and next action before raw metrics. This was later superseded by a neutral starred-run marker.

- Decision: Make A/B Changed Case Inspector a drill-down beneath the comparison flow, not the primary entry point.
  - Rationale: Case-level evidence is necessary, but starting there overwhelms reviewers.

- Decision: Show only changed cases by default in A/B comparison.
  - Rationale: The user confirmed that reviewers should inspect cases where rubric scores changed rather than all evaluation cases.

- Decision: Preserve Promptfoo as the authoritative evaluator.
  - Rationale: The website should visualize and review Promptfoo artifacts; it should not replace the CLI evaluator.

- Decision: Version logical artifacts rather than physical files.
  - Rationale: Future rubric, prompt, or dataset storage may split across multiple files.

- Decision: Treat natural-language dataset and rubric editing as draft proposal workflows.
  - Rationale: Silent source mutation would be risky for evaluation validity and version history.

- Decision: Place prompt diff behind behavior evidence in case detail.
  - Rationale: Reviewers should understand changed tutor behavior before anchoring on prompt text changes.

- Decision: Include dataset coverage and rubric meaning change as first-class product surfaces.
  - Rationale: Score movement can come from coverage problems or measurement changes, not only prompt behavior.

## 2026-06-22

- Decision: Change the PRD story from comparison-first to improvement-loop-first.
  - Rationale: The product must help users understand evaluation evolution before choosing a comparison.

- Decision: Make Evaluation Run the canonical product object.
  - Rationale: Readiness, comparison, diagnosis, and case evidence all depend on exact run context, not prompt version alone.

- Decision: Add Current Baseline Anchor and Trusted Measurement Anchor as separate concepts.
  - Rationale: The current tutor subject and the current measurement baseline are different and can drift independently.

- Decision: Distinguish Subject Artifacts from Measurement Artifacts.
  - Rationale: Prompt/model config changes aim to improve tutor behavior; Evaluation Set/rubric/evaluator config changes aim to improve measurement.

- Decision: Add Evaluation Lineage and Experiment Threads before downstream review.
  - Rationale: Users need a Git-like but reviewer-friendly history of runs, diagnoses, artifact changes, and outcomes before deciding what to compare.

- Decision: Add Diagnosis as a first-class structured object.
  - Rationale: The workflow should capture observed issue, evidence, suspected cause, target artifact, reflection, and next hypothesis before creating another artifact version.

- Decision: Add one-artifact draft guardrails and mixed-change warnings.
  - Rationale: Changing the thing being tested and the measuring stick in the same iteration makes score movement misleading.

- Decision: Keep Git-like lineage visual but avoid Git terminology in primary UI.
  - Rationale: The visual structure is useful, but non-technical reviewers need terms like Evaluation Lineage, Experiment Thread, current baseline, run, and Diagnosis.

- Decision: Keep the lineage page to Evaluation Run cards only.
  - Rationale: The user clarified that splitting Experiment Threads into run cards, diagnosis cards, artifact lanes, and next-step panels makes the page too busy. Each run card should summarize artifact versions and diagnosis, then route to Run Detail for full diagnosis work.

- Decision: Remove the separate Comparison Setup page and merge two-run selection into Evaluation Lineage.
  - Rationale: The user clarified that choosing two Evaluation Runs is a natural lineage-page action. Keeping a separate setup page adds navigation without adding value; Comparison Type remains as a compact tray after two runs are selected.

- Decision: Remove dedicated promotion logic for this version and replace it with a neutral starred-run marker.
  - Rationale: The user clarified that there is no promotion workflow in this version. A star is only a bookmark for review follow-up.

- Decision: Experiment-thread run cards should show run identity and starred state only.
  - Rationale: The user clarified that lineage cards should stay clean and show only whether each Evaluation Run is starred. Comparison roles belong in the temporary two-run comparison tray, not in the card identity.

- Decision: Remove Artifact Draft Builder as a standalone primary page.
  - Rationale: The user challenged whether the page had a unique purpose. Review showed that its useful behavior is a guardrail pattern, while real draft work belongs on artifact-specific pages.

- Decision: Add Prompt Composition and Version Log as the fourth primary page.
  - Rationale: Prompt review and prompt version history are explicit MVP requirements, but the page set lacked a prompt-specific destination after removing the generic draft page.

## 2026-06-23

- Decision: Replace Prompt Composition and Version Log with Prompt Versions.
  - Rationale: Prompt source files may not have stable structure. The workspace should not infer composition or section meaning when the source does not provide it. Prompt comparison will use prompt version selection plus source-level git diff.

- Decision: Treat Case Evidence as the selected-case detail state of A/B Changed Case Inspector.
  - Rationale: A case evidence page only has product meaning inside a specific Run A vs Run B comparison. The detail view must preserve selected comparison and case context instead of behaving like an independent workspace area.

- Decision: Keep Dataset Distribution to deterministic n-gram analysis.
  - Rationale: The LLM-assisted variable interface is too complex for the clean MVP. Reviewers only need built-in coverage dimensions plus top 1-gram, 2-gram, and 3-gram patterns to spot repeated or missing case language.

- Decision: Replace Rubric Meaning Diff with Rubric Inspect.
  - Rationale: Rubrics can span many files. The page is responsible for inspecting a selected rubric file, with source git diff as evidence and draft editing as the action.
 
- Decision: Add artifact editors to Prompt Versions and Rubric Inspect.
  - Rationale: Reviewers need to draft prompt and rubric changes on the artifact-specific pages. Git diffs remain the comparison mechanism; the rubric editor edits only the currently selected rubric file.

- Decision: Keep Rubric Inspect as rubric version selection followed by selected-file review.
  - Rationale: Users need a rubric version log to choose the base and compare rubric versions. After that choice, the page should reduce load by showing changed files, one selected file diff, and one selected file editor.
