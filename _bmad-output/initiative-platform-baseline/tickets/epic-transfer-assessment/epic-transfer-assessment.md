# Transfer assessment

## Description

A transfer assessment becomes due, is reviewed and sent by the room owner, answered and graded with two attempts, and its result messages and effect on progress are saved. This epic lists the invariants that exist today. A new feature that touches assessments, Guard, learning progress or tutor review checks itself against them.

## Outcome

For anyone changing assessments, grading or what learners see about answers: each rule is written once, with the requirement it comes from and the test or evaluation that guards it.

## Requirements

Test paths are from the repository root.

- R1 (parent R9; prd FR-32; AD-3): An assessment is due only when a learner moves a learning target from Partial to Covered by demonstrating understanding. Due is derived from progress history and never stored. One such change never produces two assessments. Reaching Covered directly from Pending, or by spontaneous transfer, makes the target complete without an assessment. While Guard is on, another assessment is open, or tutor feedback is outstanding, a due assessment waits without being lost. Guard: `tutor-system/supabase/tests/final_assessment_after_understanding.sql` (scenarios partial, pass, "open assessment blocks duplicate delivery").
- R2 (parent R9; prd FR-33, FR-34): When an assessment is due, the room owner's next request for an AI suggestion returns one assessment draft instead, and no AI suggestion is generated by that request. The draft is built from the due learning target, its evidence and the conversation; it carries a question, four options, the correct option or options, a learner explanation and the new context, and is shown to the room owner only. Generation problems are shown as errors, with no placeholder question and no fallback suggestion. A draft must have four distinct options A to D, one correct option for single-answer or two or three for multiple-answer, a question of at most two sentences and 80 words, and a non-empty learner explanation; an invalid draft cannot be sent. Guard: `tutor-system/src/__tests__/transfer_assessment.bdd.test.tsx` ("An eligible assessment bypasses the shared tutor"); `tutor-system/src/services/__tests__/assessmentRendering.test.ts`; `tutor-system/src/components/__tests__/AssessmentDraftEditor.test.tsx`.
- R3 (parent R9; prd FR-35; AD-3): The room owner sees the learning target, the new context, the question, the options, the correct answer and the learner explanation, can edit any of them, and can send the draft or reject it and write their own tutor reply. An edited draft is checked again before sending. Rejecting delivers nothing to the learner, leaves the assessment due and offered again at the next request, and shows a message naming the learning target whose progress may now be wrong and asks the room owner to check it and correct it by hand (FR-53). Learners never see a draft. Guard: `tutor-system/src/pages/__tests__/RoomPagePost.transferDraft.test.tsx` ("discards the candidate through the room context without delivering anything"; "keeps a prepared candidate hidden from learner roles").
- R4 (parent R9; prd FR-36; AD-7, C3): The server rechecks a draft before saving it. Delivery is refused if the assessment is no longer due or Guard is on. A retried delivery never creates a second question, and delivery never changes Guard; there is no assessment mode. Guard: `tutor-system/supabase/tests/final_assessment_after_understanding.sql` (error ASSESSMENT_NOT_ELIGIBLE); `tutor-system/supabase/tests/transfer_assessment_rpc_behaviour.sql` (case delivery_retry).
- R5 (parent R9; prd FR-37): Only the learner can answer their own open assessment, by selecting options and submitting. Single-answer questions use one-choice controls and multiple-answer questions use select-all controls; submitting needs a selection. Observers and other students cannot answer. Any answer that is not an option selection is refused, and there is no typed-answer, clarification or help-request path. Each assessment shows the learner's saved attempts. Guard: `tutor-system/supabase/functions/assessment-api/index.test.ts` ("observer cannot post a message or answer through the trusted API"); `tutor-system/supabase/tests/transfer_assessment_rpc_behaviour.sql` (cases wrong_actor, invalid_selection).
- R6 (parent R9; prd FR-37): While an assessment is open the learner's ordinary messaging is disabled with an explanation, and it reopens when the assessment closes. Guard: `tutor-system/src/pages/__tests__/RoomPagePost.transferLifecycle.test.tsx`; `tutor-system/scripts/browser-e2e/workflows/assessment-answer.js`.
- R7 (parent R9; prd FR-38; AD-4, AD-5, AD-7): The server grades by exact match and allows at most two attempts. While Guard is on, an answer is held, not graded, and uses no attempt; it is graded after Guard ends. A first wrong attempt leaves one attempt and learning progress unchanged. A right attempt on either try passes once; a second wrong attempt fails once. Repeated, concurrent, late or out-of-scope submissions never create extra attempts or change learning progress. The grade, progress event, attempt and result message are saved together. Guard: `tutor-system/supabase/tests/transfer_assessment_rpc_behaviour.sql` (cases first_wrong, cas_conflict, second_wrong, duplicate, third_submission, terminal_rollback); `tutor-system/supabase/tests/assessment_result_messages.sql` (scenarios guard_raw, rollback).
- R8 (parent R9; prd FR-39; AD-12, C5): Every accepted attempt creates exactly one result message with fixed text: "Correct.", "Incorrect. One attempt remaining." or, after the second wrong attempt, "Incorrect. No attempts remaining. Correct option(s): …" followed by the learner explanation. The correct answer and learner explanation appear only in the second-wrong-attempt message. Result messages are written by the server, cannot be edited by participants, survive reload, are visible to every participant and appear in exports. Guard: `tutor-system/supabase/tests/assessment_result_messages.sql`; `tutor-system/src/components/__tests__/PostComment.transfer.test.tsx`; `tutor-system/src/contexts/__tests__/roomExportBuilder.transfer.test.ts`.
- R9 (parent R9; prd FR-40; AD-1): A passed assessment makes the learning target complete. A failed one moves it to Needs review, and AI suggestions teach toward it again. After failure the learner can recover through Partial and Covered again, which makes a new assessment in another new context due. A complete target is not assessed again unless a later contradiction reopens it. Failure alone never turns on Guard. Guard: `tutor-system/supabase/tests/final_assessment_after_understanding.sql` (scenarios pass, failure_repair, contradiction).
- R10 (parent R9; prd FR-41): After an assessment ends, the room owner must send tutor feedback before that learner can get another one. Result messages, accepted AI suggestions and ratings are not tutor feedback. When several assessments are due they are offered one at a time. Guard: `tutor-system/scripts/browser-e2e/workflows/assessment-delivery.js`; `tutor-system/supabase/tests/assessment_result_messages.sql` (feedback_required checks).
- R11 (parent R9; prd FR-42; AD-12): Every participant sees the same assessment, attempts, attempts left and outcome after joining, reloading, reconnecting or using several tabs, and a late or duplicate update cannot reopen a finished assessment. Guard: `tutor-system/src/contexts/__tests__/transferAssessmentUiAdapter.lifecycle.test.ts`.
- R12 (parent R9; prd FR-31; AD-6): In-room assessment is on by default for every phishing room; the room owner can turn it off and the operator can turn assessments off everywhere. It controls only transfer assessments: learning targets, judging and learning progress work the same either way, and AI suggestions and Guard keep working. Turning it off does not close an assessment that is already open; the learner can still answer it and it is graded. Guard: `tutor-system/supabase/tests/room_assessment_default_on.sql`; `tutor-system/supabase/functions/assessment-api/index.test.ts` ("disabled feature makes no storage call").
- R13 (parent R9; prd FR-32; AD-6): A later contradiction cancels a due assessment. Changing the learning target's wording cancels an open one without using an attempt and writes one closure message. Guard: `tutor-system/supabase/tests/final_assessment_after_understanding.sql` (scenarios contradiction, stale_open); `tutor-system/supabase/tests/assessment_result_messages.sql` (scenario target_edit).
- R14 (parent R9; prd FR-33, FR-34, NFR-9): As for every AI job (NFR-9), the quality of the output is governed by an AI behavior specification and checked by evaluation, not by code tests. For assessment drafts, whether the new context differs meaningfully from the scenario, and the quality of assessment drafts, are governed by the tutor behavior specification T09.1 to T09.6 and checked by its evaluation suite. Guard: `evals/promptfoo/v1/transfer/metric-registry.json` with `evals/promptfoo/rubrics/v1/medium_transfer_quality.md` and `evals/promptfoo/rubrics/v1/assessment_item_validity.md`.
- R15 (parent R9; prd FR-43): The AI assistant gets assessment outcomes only from the saved conversation, and generates no AI suggestion while the learner's result messages are still being saved. Guard: none.
- R16 (parent R9; prd NFR-3; C5, C6): Correct answers and learner explanations stay private until a second wrong attempt. The reasoning behind a transfer assessment and raw AI output are never visible to participants. Reasons and instruction labels are visible to the room owner only. AI provider credentials never reach the browser. Guard: `tutor-system/supabase/tests/assessment_result_messages.sql`; `tutor-system/supabase/tests/private_transfer_assessment_storage_migration.sql`.

## Constraints

- No AI-generated text reaches a learner unless the room owner sends it (constitution C1).
- Grades, attempts and progress changes are decided on the server from recorded evidence; the browser never decides them (constitution C3).
- Private assessment material reaches participants only at its publication point, so a transfer assessment stays a valid check (constitution C5; AD-12).
- Item progress changes only through the learning-event writer (model and assessment events) or the manual progress-edit writer (the owner's edit); assessment state changes only through the reviewed-send function (create), the assessment grading function (grade and close) and the cancellation functions. No new writer is added: not in the client, not in another database function, not in an Edge Function. History tables are append-only (AD-1). Today these are `apply_learning_event_v1`, `edit_room_checklist_v1`, `send_reviewed_tutor_response_v4` and `process_assessment_message_v2`.
- The assessment grading function commits the grade, the progress event, the attempt row and the result message in one transaction. Each assessment has one terminal event key. The learner's answer message is saved in an earlier transaction (AD-4).

## Boundaries

- Touch point: server authority, repeatable requests and the version handshake — owner: epic-platform-guarantees
- Touch point: result messages in the shared conversation, which are never rated — owner: epic-conversation
- Touch point: learning progress states and events — owner: epic-learning-progress
- Touch point: Guard and owner-only controls — owner: epic-supervision-and-guard
- Touch point: the review and send flow that an assessment draft replaces — owner: epic-ai-suggestions
- Touch point: result messages in exports — owner: epic-exports-and-records
- Not here: transfer assessments in cyberbullying rooms, which are refused.
- Must not change: the correct answer and learner explanation stay private until the second wrong attempt.
