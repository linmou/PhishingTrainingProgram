## 2. Questions

### (a) Guard turned on while an assessment is open
- Graded? No. The pure resolver returns `guard_deferred` (ORCH:168-173) after the duplicate, feedback, not-delivered and stale-hash checks (ORCH:151-167) and before any parsing or grading; the edge then calls `record_transfer_assessment_processing_v1` (EDGE:610-617), which stores code guard_deferred in `transfer_assessment_processing`, consumes no attempt (M21:881-891). Context supplies `guard_mode` (M21:768). Exception: if Guard flips on after the edge fetched context but before commit, `process_assessment_message_v2` locks the room row first (M17:241) so the flip waits; once inside, it grades and only the progress change is deferred (below).
- Result message saved? Not for a guard-deferred answer (`result_message` NULL, M21:886; the edge only demands a result message when an outcome or assisted/cancelled code exists, EDGE:212). When graded just before Guard, yes, with `progress_deferred=true` (M17:157, M17:295).
- Does progress wait? Yes. `apply_learning_event_v1` inserts the event, marks `deferred_guard` and returns PROGRESSION_LOCKED (M21:417-420); the assessment still becomes passed/failed and the attempt row is `deferred` (M17:277-294). Direct item/evidence/update/checklist writes are blocked by `reject_guard_progress_mutation` (M21:1695-1700; live triggers `block_guard_*`).
- Events gathered during Guard: applied later, not dropped, with exceptions. Analysis events and the `analysis:<msg>` marker are stored deferred (M21:660-669, M21:709-710). Trigger `transfer_replay_guard` fires AFTER UPDATE OF guard_mode (M21:987) and replays in `created_at` order (M21:794-795). Per-event outcome: rejected if the target text changed or the item was deleted (M21:801-809); assessment events rejected if the scope does not match (M21:810-819) or the item hash changed, which also cancels the assessment (M21:820-839); otherwise the original payload is re-applied and transition rules re-run against the then-current state, so an event can become no_change (M21:842-847, M21:440-443). Un-graded guard-deferred answers are re-run by client catch-up on room load (`RoomContext.tsx:589`) or by tutor `read_review` (EDGE:677-688); the readiness query treats a guard_deferred row as unhandled once Guard is off (M21:910). Whether the live client always runs catch-up: UNCONFIRMED.

### (b) What cancels or closes a due or open assessment
A "due" assessment has no row, so nothing to close; it simply stops being due when the derivation fails (M14:12-31).
- Progress state change, wording change, delete, manual progress edit, contradiction: trigger `cancel_changed_target_assessments` on UPDATE OF status, understanding_level, area_text, deleted sets lifecycle cancelled and the question message cancelled (M14:224-248). It skips the assessment being applied (M14:237), so a pass/fail does not cancel itself. Contradiction and manual edits reach it through the item UPDATE (M21:451; M21:1586, 1595, 1602). Closure message written: yes, trigger `publish_assessment_cancellation` calls the closure writer on any lifecycle -> cancelled (M17:209-225), reason target_changed, or progress_invalidated if it was previously passed/failed (M17:213-217), text at M17:192-196.
- Priority or notes edits: do not cancel (trigger column list M14:247; hash fields M14:252-255).
- Manual edit while Guard is on: rejected by the Guard trigger (M21:1695-1700). Cyberbullying rooms: manual edit unsupported (M21:1533).
- Assisted answer (free text instead of option): `cancel_transfer_assessment_v1`, closure reason assisted, no attempt used (M17:301-331; ORCH:202-206).
- In-room assessment turned off (`transfer_learning_enabled=false`): no cancellation. No trigger on that column (live trigger list on `rooms`: none for it); live functions that read the flag are only prepare_transfer_assessment_context_v1, send_reviewed_transfer_assessment_v1, get_transfer_message_analysis_context_v1, initialize_transfer_checklist_v1 and the practice-identity trigger. So an open assessment stays open and can still be answered and graded (`process_assessment_message_v2` never checks the flag, M17:227-298); only new preparation, sending and message analysis are refused. No closure message.
- Operator flag `TRANSFER_ASSESSMENT_ENABLED` off: edge returns ASSESSMENT_FEATURE_DISABLED for every operation except clear_chat_history (EDGE:664); default true (EDGE:832; `.env.example:21`). No DB change, no closure message, open assessments remain open but cannot be posted to or graded until re-enabled.
- Clear chat history deletes assessments, attempts and messages (M17:544-550).

### (c) Atomicity of grade, progress change and result message
Yes inside the server function. `process_assessment_message_v2` is one plpgsql call (one transaction) that, for a terminal outcome, calls `apply_learning_event_v1`, updates the assessment and question message, inserts the attempt row, writes the result message and stores it into `authoritative_result` (M17:272-296). Any exception rolls all back. Caveats: the student's answer message is created in an earlier, separate transaction (`post_assessment_message_v2`, M13:195-233) and the client calls `process_message` afterwards (`RoomContext.tsx:746`); under Guard the progress part is deferred and applied in a later transaction (see a); on duplicate calls the result message is re-created if missing (M17:248-251).

### (d) Discard of an assessment draft
Discard is UI-local: `onCancel={clearAISuggestion}` with the comment "there is no draft row, so nothing is persisted" (`src/pages/RoomPagePost.tsx:891-896`; button at `AssessmentDraftEditor.tsx:293-295`). No server call. The assessment stays due because due-ness is derived from progress (M14:12-31) and `prepare_transfer_assessment_context_v1` has no write to assessment state (M14:259-371; its `p_request_id` is unused in the body shown). It is re-offered at the next prepare/AI suggestion request as long as: no assessment is open, no terminal assessment awaits tutor feedback, Guard is off (M21:133-149, M21:181). Server residue: provider-attempt audit rows (`record_transfer_provider_attempt_v1`, EDGE:549-550). The legacy suggestion box "Reject" records `ai_suggestion_feedback` 'rejected' (`RoomPagePost.tsx:510-513`) and is a separate path.

### (e) Idempotency and concurrency
- Answer messages: unique `assessment_request_id` (`20260929090000_staging_assessment_runtime.sql:7`) with replay lookup (M13:212-216). The client generates a fresh request id per call (`transferAssessmentService.ts:313-314`, `defaultRequestId` 275-278), so a user retry is a new message unless a caller reuses the id (UNCONFIRMED). Two tabs or double submit can therefore create two answer messages for one open assessment (`post_assessment_message_v2` only requires lifecycle open, M13:222-223); the UI disables a second submission (comment in `RoomContext.tsx`, UNCONFIRMED how strictly).
- Grading: keyed on `answer_message_id`; second call returns stored `authoritative_result` as duplicate (M17:247-251). Room row then assessment row locked FOR UPDATE (M17:241-242). Compare-and-set on `attempt_count` and lifecycle returns CONCURRENT_MODIFICATION (M17:252-253); edge retries up to 3 times (EDGE:564, 601, 615, 634). Outcome and transition are recomputed server-side and must match the edge's (M17:262-266); stale item hash raises INVALID_TRANSITION (M17:255-257). A third answer after terminal is recorded as rejected "duplicate" without consuming an attempt (ORCH:151-156; EDGE:609-617).
- Events: advisory lock and unique `dedupe_key` (M21:384-386); the terminal event key is `assessment:<id>`, so one terminal event per assessment (M17:272-273); analysis serialized per message by advisory lock (M21:652) and marker `ON CONFLICT DO NOTHING` (M21:711). Result and closure messages unique by index (M17:62-69).
- Delivery: `ASSESSMENT_ALREADY_OPEN` check under the room row lock (M21:292, M21:329-330); reviewed send is idempotent on `assessment_request_id` (M21:300-305).
- Manual edit idempotent on request id via advisory lock and `checklist_updates.event_id` (M21:1539-1548).
- Lock order: process path takes room then assessment then item (M17:241-242, M21:387-393 inside apply); analysis path takes room first (M21:660) before events. A lock-order inversion elsewhere: UNCONFIRMED, none seen.
